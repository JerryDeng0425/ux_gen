# Step 05：完善产物与元数据

## 目标

建立稳定、原子、可审计的产物协议，使每个关键点都能追溯来源、时点、状态和完整性。

## 前置条件

- Step 04 能产生最终 HTML 字符串和完整 capture payload。
- 输出目录权限已在启动阶段验证。

## 实施任务

1. 实现 run 目录和关键点文件的安全命名。
2. 冲突时使用递增序号或唯一时间戳，不覆盖历史文件。
3. 写出 HTML、PNG、JSON，并计算 HTML/PNG SHA-256。
4. JSON 记录场景、关键点、三个时间、URL、viewport、DPR、滚动、节点数、字节数和 warnings。
5. 三类文件全部完成后才提交关键点状态。
6. 所有最终文件采用临时文件 + 原子重命名。
7. 每次状态变化原子更新 `run-summary.json`。
8. 清理本次失败产生的临时文件，但不删除任何成功历史产物。

## 交付物

- Artifact Writer、命名器和 hash 工具。
- artifact JSON schema。
- 原子写入、冲突和故障注入测试。

## 可验收项

| ID | 验证方法 | 通过标准 | 验收证据 |
| --- | --- | --- | --- |
| AC-05-01 | 完成一个关键点 | `.html`、`.png`、`.json` 同名对应且均非空 | 产物清单 |
| AC-05-02 | 复算 HTML/PNG SHA-256 | 与 metadata 中记录完全一致 | hash 校验输出 |
| AC-05-03 | 在三次写入阶段分别注入失败 | 关键点不被标记完成，最终目录无半文件 | 故障注入报告 |
| AC-05-04 | 同一关键点连续采集三次 | 三组产物都保留，命名稳定且无覆盖 | 文件名和 hash |
| AC-05-05 | 检查 JSON 必填字段 | PRD FR-07 所列字段全部存在且类型正确 | schema 校验报告 |
| AC-05-06 | 比较 summary 与关键点 JSON | 状态、文件引用、warning 数量一致 | 一致性测试 |
| AC-05-07 | 强制结束进程后重新检查 | 已提交产物完整；临时文件不会被误认为成功结果 | 恢复测试记录 |
| AC-05-08 | 使用含非法文件名字符的关键点名称 | 写入成功，路径不越过 run 目录 | 路径安全测试 |

## 完成判定

任何失败都不会形成“状态成功但产物不全”；历史文件无覆盖；metadata 和 summary 可通过 schema 及交叉一致性校验。
